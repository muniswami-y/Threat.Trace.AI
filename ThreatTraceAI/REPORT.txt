1. EXECUTIVE SUMMARY
================================================================================

ThreatTrace AI is a full-stack, AI-powered email threat detection and forensic
intelligence platform. It is designed for cybersecurity professionals, SOC
(Security Operations Center) analysts, and law enforcement digital forensics
teams.

WHAT IT DOES:
  - Accepts a raw email (pasted text, .eml content, or DOM-scraped from Gmail)
  - Runs it through a 14-step automated analysis pipeline
  - Produces an explainable risk score (0-100) with every signal traced to a
    specific, human-readable evidence point
  - Cryptographically seals the forensic evidence using ECDSA + SHA-256
  - Anchors a tamper-proof hash to the Polygon Amoy blockchain for legal
    chain-of-custody
  - Generates a downloadable forensic report in JSON and styled HTML
  - Dispatches SOC alerts in CEF format (Splunk/Sentinel), Jira tickets,
    and Slack/Teams notifications

KEY DIFFERENTIATORS:
  - EXPLAINABILITY: Every risk point is tied to a concrete, readable signal —
    no black-box ML, every rule can be shown to a judge or investigator
  - CRYPTOGRAPHIC INTEGRITY: Evidence is ECDSA-signed and blockchain-anchored,
    making post-hoc tampering detectable and provable in court
  - GMAIL NATIVE: The Chrome extension scrapes Gmail's DOM without requiring
    SMTP relay access or email forwarding
  - END-TO-END SECURITY: Salt+pepper ID obfuscation, SSRF protection, AES-GCM
    encrypted dossiers, and homoglyph detection all work together

5. CORE ANALYSIS PIPELINE — 14 STEPS
========================================================================

The analyze.py route orchestrates a full 14-step async pipeline on every
email submission received at POST /api/analyze.

REQUEST SCHEMA (AnalyzeRequest):
  Field             | Type          | Description
  ------------------|---------------|--------------------------------------
  email_text        | str (required)| Raw email body or full .eml content
  subject           | str (optional)| Override for subject line
  from_header       | str (optional)| Override for sender
  links             | list (optional)| [{display, href, unwrapped}] from ext.
  resolve_domain_ip | bool          | Whether to do live DNS resolution
  save_case         | bool          | Whether to persist to database


------------------------------------------------------------------------
5.1 STEP 1 — EMAIL PARSING
------------------------------------------------------------------------
Service: email_parser.py

Parses the raw email text to extract structured fields:
  - subject         : Subject line text
  - from_header     : Full "From:" header value
  - sender_email    : Extracted email address from From header
  - sender_name     : Display name from From header
  - to_header       : Recipient address
  - headers         : Dictionary of all SMTP headers (key: value)
  - body_text       : The human-readable plain text body

If the caller provides subject or from_header overrides in the request
payload, those values replace the parsed ones. The sender_email is also
re-extracted from from_header if it contains an "@" symbol.


------------------------------------------------------------------------
5.2 STEP 2 — HEADER ANALYSIS (SPF / DKIM / DMARC)
------------------------------------------------------------------------
Service: header_analyzer.py
Function: analyze_headers(headers, sender_email)

Determines if REAL headers are present by checking for:
  Authentication-Results, ARC-Authentication-Results, Received, Message-ID

MODE A — REAL HEADER ANALYSIS (headers available):
  Check                          | Points | Factor Added
  -------------------------------|--------|-----------------------------
  SPF=fail or SPF=softfail       | +25    | "SPF failed or soft-failed"
  SPF=none                       | +12    | "No SPF record for sender domain"
  SPF=pass                       |  0     | "SPF passed ✓"
  No clear SPF result            |  +8    | "No clear SPF result in headers"
  DKIM=fail                      | +20    | "DKIM signature failed"
  DKIM (not present)             |  +5    | "No clear DKIM result"
  DKIM=pass                      |  0     | "DKIM passed ✓"
  DMARC=fail                     | +25    | "DMARC failed"
  DMARC=pass                     |  0     | "DMARC passed ✓"
  From ≠ Return-Path             | +15    | "From address does not match Return-Path"
  Missing Message-ID             |  +5    | "Missing Message-ID header"
  PHP/Python/script in X-Mailer  | +10    | "Suspicious mailer string"
  More than 6 Received hops      |  +5    | "Unusually long relay chain (N hops)"

  MAX CAP: 60 points

MODE B — HEURISTIC ANALYSIS (Gmail web client, no raw headers):
  This is the typical case when analyzing via the Chrome extension.
  Adds the factor "Email headers not available (web client analysis)".
  Then checks:
    - Does sender use a free email provider?              (+3 if yes)
    - Is the local part of sender >20 chars?             (+5)
    - Is the digit ratio of local part >0.6?             (+8)
    - Does local part start with a safe service prefix?   (0 — whitelisted)
      Safe prefixes: noreply, no-reply, notifications, info, support,
                     admin, contact

  MAX CAP: 60 points (shared with Mode A cap)


------------------------------------------------------------------------
5.3 STEP 3 — DISPLAY NAME SPOOFING DETECTION
------------------------------------------------------------------------
Service: header_analyzer.py
Function: analyze_display_name_spoofing(display_name, sender_email)

A DEDICATED CHECK separate from step 2. Compares what the email client
SHOWS to the user (the display name) against the ACTUAL email domain.

ATTACK EXAMPLE:
  Display name shown  : "PayPal Security Team"
  Actual email        : xjq93bz@gmail.com
  Detection           : "Display name impersonates 'paypal' but uses free
                         email provider 'gmail.com' — likely spoofing"
  Points              : +22

SECONDARY CHECK:
  Detects display names that contain a full email address inside them.
  Phishing kits sometimes put a legitimate email address in the display
  name field to confuse mail clients into showing the wrong sender.
  Example display name: "PayPal <security@paypal.com>"
  but actual email is: attacker@evil.com
  Points: +12

MONITORED BRANDS (24 total):
  paypal, apple, microsoft, google, amazon, netflix, facebook, instagram,
  whatsapp, linkedin, twitter, chase, wells fargo, bank of america,
  citibank, hsbc, dropbox, adobe, dhl, fedex, ups, usps, irs,
  government/police

MAX CAP: 25 points


------------------------------------------------------------------------
5.4 STEP 4 — IOC EXTRACTION
------------------------------------------------------------------------
Service: ioc_extractor.py
Function: extract_iocs(body, headers, extension_links)

IOC = Indicators of Compromise. Extracts all suspicious network artifacts.

URLs:
  - Extracted from body + headers using regex (via validators.py)
  - Extension-provided link objects merged in (avoids duplicates)
  - All Google redirect wrappers unwrapped:
      https://www.google.com/url?q=REAL_URL → REAL_URL
  - Filtered: tel:, mailto:, sms:, callto:, javascript:, # are EXCLUDED

IPs:
  - Extracted from body text using IPv4 pattern regex
  - Additionally extracted from Received: headers using a specialized regex:
      r'(?:from|by)\s+\S+\s+\((?:[^)]*?)[\[\(]?(\d{1,3}\.\d{1,3}...)'
    This pattern finds the SMTP-origin IP — the real sending server IP
    that first injected the email into the relay chain.
  - PRIVATE IPs FILTERED OUT (non-routable, non-useful for attribution):
      10.x, 127.x, 172.16-31.x, 192.168.x, 169.254.x, 0.x

DOMAINS:
  - From URL parsing (using tldextract for accurate registered domain)
  - From direct domain mentions in text (regex for common TLDs)
  - From email addresses in the body (@domain.com extraction)

DNS RESOLUTION:
  - Up to 8 domains resolved via socket.gethostbyname()
  - Resolved IPs added to the IP list for geolocation
  - Known safe domains skipped: google.com, googleapis.com, gstatic.com

RETURN VALUE:
  {
    "urls": [...],          # Sorted, deduplicated
    "domains": [...],       # Sorted, deduplicated
    "ips": [...],           # Sorted, deduplicated (public only)
    "header_ips": [...],    # True SMTP-origin IPs only
    "emails": [...],        # Email addresses found in body
    "resolved_ips": {...}   # {domain: ip} mapping from DNS
  }


------------------------------------------------------------------------
5.5 STEP 5 — URL UNMASKING & DEOBFUSCATION ENGINE
------------------------------------------------------------------------
Service: url_unmasker.py
Function: unmask_urls(urls, max_hops=5, timeout=4.0)

The most sophisticated service. Handles multiple obfuscation layers.

A. MULTI-LAYER URL DECODING (decode_obfuscated_url):
   - urllib.parse.unquote() called TWICE to handle double URL encoding
     Example: %2520 → %20 → space (attacker trick)
   - Detects embedded Base64 data URIs:
     data:text/html;base64,PHNjcmlwdD...
     Decodes the base64, extracts real URL from decoded HTML
   - Strips whitespace

B. GOOGLE REDIRECT UNWRAPPING (unwrap_google_redirect):
   Gmail wraps EVERY external link:
   https://www.google.com/url?q=http://evil.xyz/login&sa=D&...
   The function parses the 'q' query parameter to get the real URL.
   Also handles AMP proxy: https://amp.google.com/...?url=...

C. SSRF PROTECTION (is_ssrf_safe):
   Before making ANY HTTP request, the hostname is resolved to IP
   via socket.getaddrinfo(). ALL resolved IPs are checked against
   9 private/reserved network ranges:
     - 127.0.0.0/8   (Loopback)
     - 10.0.0.0/8    (Private Class A)
     - 172.16.0.0/12 (Private Class B)
     - 192.168.0.0/16(Private Class C)
     - 169.254.0.0/16(Link-Local / AWS/GCP/Azure metadata endpoint)
     - 0.0.0.0/8     (Current network)
     - ::1/128       (IPv6 loopback)
     - fc00::/7      (IPv6 unique local)
     - fe80::/10     (IPv6 link-local)
   If ANY resolved IP is in a private range:
     → Request is BLOCKED with error: "SSRF_BLOCKED: Host X resolves
       to internal/cloud-metadata IP"
     → No HTTP request is made

D. HOMOGLYPH / PUNYCODE DETECTION (detect_homoglyphs):
   Catches Internationalized Domain Name (IDN) lookalike attacks.
   Example: pаypal.com (Cyrillic 'а' instead of Latin 'a')
   - Checks for 'xn--' Punycode prefix in domain
   - Compares .encode('idna') output to detect Unicode script mixing
   - Flags if a known brand name appears in a homoglyph domain

E. SAFE MULTI-HOP REDIRECT FOLLOWING:
   - Uses HEAD requests only (never GET) — avoids downloading payloads
   - Follows up to 5 redirect hops
   - Tracks full redirect_chain[] array
   - Detects cross-domain redirects (domain-A.com jumps to domain-B.com)
   - Uses custom User-Agent: "ThreatTraceAI/2.0 (Forensic Analysis Bot)"

RESULT PER URL:
  {
    "original":             "https://www.google.com/url?q=http://evil.xyz",
    "unwrapped":            "http://evil.xyz/login",
    "final":                "http://evil.xyz/phish",
    "redirect_count":       1,
    "status":               301,
    "is_google_wrapped":    true,
    "cross_domain_redirect":false,
    "redirect_chain":       ["http://evil.xyz/login", "http://evil.xyz/phish"],
    "ssrf_safe":            true,
    "homoglyph":            {"is_punycode": false, "is_homoglyph_spoof": false}
  }

------------------------------------------------------------------------
7.1 ECDSA KEY MANAGEMENT
------------------------------------------------------------------------

KEY ALGORITHM: NIST P-256 (SECP256R1)
  - 128-bit security level (equivalent to RSA-3072)
  - Used by TLS 1.3, Bitcoin, Ethereum, and most modern PKI
  - Fast signing (~0.1ms) and verification (~0.3ms)

KEY FILES:
  backend/app/keys/forensic_authority_private.pem  (PKCS8 format)
  backend/app/keys/forensic_authority_public.pem   (SubjectPublicKeyInfo)

LIFECYCLE:
  - On FIRST startup: new keypair generated and saved to disk
  - On SUBSEQUENT startups: existing keys loaded from PEM files
  - This gives ThreatTrace AI a persistent forensic authority identity

KEY FINGERPRINT FORMAT:
  TT-SECP256R1-XXXX:XXXX:XXXX:XXXX
  (SHA-256 of DER-encoded public key, first 16 hex chars formatted as 4 groups)


------------------------------------------------------------------------
7.2 CANONICAL SHA-256 HASHING
------------------------------------------------------------------------

Function: canonical_case_dict(case) + compute_canonical_hash(case)

Before hashing, case data is NORMALIZED into a deterministic canonical form:

  Step 1: URLs → extract final destination strings → sort alphabetically
  Step 2: Domains → sort alphabetically
  Step 3: IPs → sort alphabetically
  Step 4: Risk factors → sort alphabetically
  Step 5: String fields → strip whitespace, lowercase (sender, recipient)
  Step 6: Body text → hash to SHA-256 separately; only the hash goes
          in the canonical dict — body content itself never included

  CANONICAL DICT FIELDS:
    case_id, subject, sender, recipient, body_hash,
    risk_score, risk_level, risk_factors, urls, domains, ips,
    recommendation, origin_ip

SERIALIZATION:
  json.dumps(canonical, sort_keys=True, separators=(",",":"))
  → NO spaces, keys always in alphabetical order
  → Identical output on every machine, every Python version

FINAL HASH:
  hashlib.sha256(serialized.encode("utf-8")).hexdigest()


------------------------------------------------------------------------
7.3 DIGITAL SIGNATURE (ECDSA SECP256R1)
------------------------------------------------------------------------

SIGNING:
  digest_hex = SHA256(canonical_json)
  signature  = ECDSA_SIGN(private_key, digest_bytes, ECDSA(SHA256()))

VERIFICATION:
  pubkey.verify(sig_bytes, digest_bytes, ECDSA(SHA256()))
  → Raises InvalidSignature if ANY byte of the sealed data was changed

The signature is stored as a lowercase hex string prefixed with "0x".

WHY THIS MATTERS:
  If an attacker tries to change even one character of a sealed case
  (e.g., change risk_score from 95 to 0 to clear a QUARANTINE verdict):
    → canonical_hash will be completely different
    → ECDSA_VERIFY will fail → "CRITICAL SECURITY ALERT: tampered"
    → The original sealed hash on blockchain will not match
  The forgery is provably detectable.


------------------------------------------------------------------------
7.4 CRYPTOGRAPHIC EVIDENCE SEAL
------------------------------------------------------------------------

Function: seal_case(case_dict)

Returns a complete forensic seal package:
  {
    "sealed": true,
    "canonical_hash": "0x3f7a1b...",      SHA-256 of canonical JSON
    "body_hash": "0xa9c2f1...",            SHA-256 of email body
    "signature": "0x304502...",            ECDSA-SECP256R1 signature
    "algorithm": "ECDSA-SECP256R1-SHA256",
    "public_key_fingerprint": "TT-SECP256R1-14B6:1DE7:CEE4:E003",
    "public_key_pem": "-----BEGIN PUBLIC KEY-----...",
    "merkle_root": "0xf0a3b2...",
    "blockchain_tx": "0xe9b1a4...",
    "blockchain_network": "Polygon Amoy (Chain ID 80002)",
    "timestamp": "2026-09-16T06:30:00Z",
    "canonical_fields": { ... }
  }

MERKLE ROOT:
  merkle_payload = f"{canonical_hash}:{timestamp}:{fingerprint}"
  merkle_root = SHA256(merkle_payload.encode("utf-8"))
  
  Binds the evidence hash to a specific time and forensic authority
  key fingerprint. Proves WHEN the evidence was sealed, independent
  of the blockchain timestamp.


------------------------------------------------------------------------
7.5 TAMPER DETECTION ENGINE
------------------------------------------------------------------------

Function: verify_seal(current_case, signature_hex, public_key_pem, expected_hash)

  Step 1: Re-compute canonical_hash from current_case state
  Step 2: Compare to expected_hash (from original seal)
  Step 3: Run ECDSA verify(current_hash, signature, public_key)
  
  If Step 2 fails → "Canonical SHA-256 digest does not match. Evidence
                      was altered after sealing."
  If Step 3 fails → "ECDSA digital signature verification failed."
  If both pass    → "Cryptographic integrity verified. 100% untampered."

Function: simulate_tamper_attack(case)

  DEMONSTRATION MODE:
  1. Seals the original case (gets signature + canonical_hash)
  2. Creates tampered copy:
     - sender changed to "legitimate-bank@trusted.com"
     - risk_score changed to 0
     - recommendation changed to "ALLOW"
  3. Runs verify_seal() against original signature
  4. Returns:
     {
       "breach_detected": true,
       "signature_status": "REJECTED (Invalid Signature)",
       "alert": "CRITICAL SECURITY ALERT: Cryptographic evidence
                 tampering detected!"
     }

7.6 AES-256-GCM END-TO-END ENCRYPTED VAULT

Function: decrypt_dossier(envelope_dict, passphrase)

9. SALTING & PEPPERING — ID OBFUSCATION
========================================================================

File: backend/app/utils/salting.py

PROBLEM SOLVED:
  Without salting, case IDs like "TT-2026-00000001", "TT-2026-00000002"
  are predictable. An attacker could enumerate all cases by trying
  sequential IDs against /api/reports/{case_id}/generate.

TERMINOLOGY:
  SALT   : Random data PREPENDED to an ID (stored in DB, non-secret)
  PEPPER : Random data APPENDED to an ID (stored in DB, extra entropy)

RANDOM SOURCE:
  secrets.choice() — Python's CSPRNG (Cryptographically Secure
  Pseudo-Random Number Generator), backed by os.urandom() / OS entropy.
  NEVER uses the insecure random module.

ALPHABET: a-z A-Z 0-9 (62 characters — URL-safe, human-readable)

FORMAT:
  [4-char salt]_[base_id]_[4-char pepper]

EXAMPLES:
  Base ID               → Salted ID
  TT-2026-3F7A912B      → Xk9f_TT-2026-3F7A912B_9p2Q
  RPT-2026-A4C2F109     → aB3z_RPT-2026-A4C2F109_kL7w

SECURITY:
  Salt+pepper length: 4 + 4 = 8 characters
  Alphabet size: 62 characters
  Combinations: 62^8 = 218,340,105,584,896 (218 trillion)
  → Brute-force enumeration is completely impractical

FUNCTIONS:
  generate_salt(length=4)
    → Returns 4-char cryptographically random alphanumeric string

  generate_pepper(length=4)
    → Same as salt, distinct role (appended instead of prepended)

  apply_salt_pepper(base_id, salt_length=4, pepper_length=4)
    → Returns (salted_id, salt, pepper)
    → Used in analyze.py and reports.py

  strip_salt_pepper(salted_id, salt, pepper)
    → Recovers original base_id from stored salt+pepper
    → Used for forensic recovery and internal cross-reference
    → Raises ValueError if pattern doesn't match

STORAGE:
  case_salt and case_pepper columns in the Case table.
  Both values are persisted so the original base ID can always
  be recovered for internal audit or cross-referencing.

12. SSRF PROTECTION LAYER
========================================================================

SSRF = Server-Side Request Forgery
An attack where a malicious URL in an email tricks the analysis server
into making HTTP requests to internal infrastructure.

ATTACK SCENARIO:
  Attacker includes URL: http://169.254.169.254/latest/meta-data/
  (AWS EC2 metadata endpoint — exposes cloud credentials)
  Without protection: server fetches the URL → cloud keys exposed.

PROTECTION IMPLEMENTATION (url_unmasker.py: is_ssrf_safe):
  Before ANY HTTP request:
  1. Resolve hostname to ALL IPs via socket.getaddrinfo()
  2. For each resolved IP, check against 9 protected ranges using
     ipaddress.ip_network membership test
  3. If ANY IP is in a protected range → BLOCK

PROTECTED RANGES:
  127.0.0.0/8     Loopback (localhost)
  10.0.0.0/8      Private Class A (corporate networks)
  172.16.0.0/12   Private Class B (Docker, AWS VPC)
  192.168.0.0/16  Private Class C (home/office networks)
  169.254.0.0/16  Link-Local (AWS metadata, GCP metadata, Azure IMDS)
  0.0.0.0/8       Current network (invalid/unspecified)
  ::1/128         IPv6 loopback
  fc00::/7        IPv6 unique local
  fe80::/10       IPv6 link-local

Also uses HEAD requests only (never GET) to prevent downloading
binary malware payloads during redirect following.
